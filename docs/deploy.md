# Деплой Starfall

Образ збирається й публікується автоматично за тегом `v*`:
`ghcr.io/vlepekha/starfall`. Лишилося дати йому де працювати.

Весь процес — приблизно п'ять хвилин, і майже весь він у браузері.

---

## Крок 1. Створити сервіс на Render

Render обраний тому, що в репозиторії вже лежить [`render.yaml`](../render.yaml),
і налаштовувати руками не доведеться **нічого** — жодного поля, жодної змінної.

1. Відкрити [dashboard.render.com](https://dashboard.render.com) і увійти.
   Найшвидше — «Sign in with GitHub»: репозиторій і так на GitHub, і Render
   одразу побачить його у списку.
2. **New → Blueprint**.
3. У списку репозиторіїв обрати **`vlepekha/starfall`**. Якщо його немає —
   натиснути «Configure account» і дати Render доступ до цього репозиторію.
4. Render прочитає `render.yaml` і покаже, що створить один web-сервіс
   `starfall`. Натиснути **Apply** / **Create**.
5. Чекати перший деплой: приблизно 3–6 хвилин. Збірка образу йде на боці
   Render, у вкладці Logs видно ті самі кроки, що й у GitHub Actions.

Адреса з'явиться вгорі сторінки сервісу й виглядатиме так:
`https://starfall-xxxx.onrender.com`.

> **Нічого не питає про ALLOWED_ORIGINS — і це правильно.** Render уміє
> запитувати значення при створенні (`sync: false`), але робить це **до**
> того, як сервіс існує, тобто коли адреси ще немає — а саме її туди й
> треба було б вписати. Тому сервер бере власне походження зі змінної
> `RENDER_EXTERNAL_URL`, яку Render підставляє сам.

## Крок 2. Перевірити, що все справді працює

Замініть `URL` на свою адресу.

```bash
curl -s URL/health
```

Очікувано: `"ok":true`, `"env":"production"` і `"sha"` — хеш коміту, з якого
зібрано. Саме за цим полем перевіряють, що розгорнуто потрібну версію.

```bash
curl -s -o /dev/null -w '%{http_code}\n' URL/ready     # 200
curl -s URL/metrics | head -3                          # starfall_up 1
```

Перевірка, що сервер не пускає чужі сайти:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  -H "Connection: Upgrade" -H "Upgrade: websocket" \
  -H "Sec-WebSocket-Version: 13" -H "Sec-WebSocket-Key: AAAAAAAAAAAAAAAAAAAAAA==" \
  -H "Origin: https://evil.example.net" \
  URL/ws
```

Має бути **403**. Якщо раптом `101` — значить сервер нікого не перевіряє;
напишіть про це, розбиратимемось.

І головне: відкрити `URL` у браузері, зайти в кімнату, політати. У вкладці
Network має бути з'єднання `wss://…/ws` — саме `wss`, не `ws`.

## Крок 3. Вписати адресу в README

```bash
cd ~/Desktop/starfall-lab01
sed -i '' 's|<!-- PUBLIC_URL --> `https://…`|<!-- PUBLIC_URL --> https://ВАША-АДРЕСА|' README.md
git add README.md && git commit -m "README: жива адреса" && git push
```

## Крок 4 (необов'язковий). Замкнути автодеплой

Поки цього немає, Render сам перезбирає сервіс на кожен push у `main` —
цього достатньо. Крок нижче потрібен, щоб деплой ішов **за тегом версії**,
як вимагає умова лаби, і щоб GitHub Actions ще й перевіряв результат.

| Де | Що додати | Значення |
| --- | --- | --- |
| Render → сервіс → Settings → Deploy Hook | скопіювати адресу | — |
| GitHub → Settings → Secrets and variables → Actions → **Secrets** | `DEPLOY_HOOK_URL` | скопійована адреса |
| там само → **Variables** | `PUBLIC_URL` | `https://ваша-адреса` |

Після цього `git push origin v1.0.4` сам збере образ, покладе в GHCR, смикне
Render і **перевірить**, що на живій адресі `/health` віддає той самий SHA.
Без останньої перевірки «задеплоїли» означало б лише «надіслали запит».

## Про безкоштовний план Render

Це важливо знати **до** захисту:

- сервіс засинає після **15 хвилин** без вхідного трафіку (повідомлення у
  вже відкритих WebSocket теж вважаються трафіком);
- пробудження триває **близько хвилини**;
- 750 безкоштовних годин на місяць на весь обліковий запис;
- Render може перезапустити безкоштовний сервіс будь-коли — гравці
  побачать повідомлення «сервер перезапускається» й повернуться в лобі,
  бо саме цей сценарій у грі оброблений.

**Перед захистом відкрийте адресу хвилини за дві**, щоб процес прокинувся.

## Якщо щось пішло не так

| Симптом | Найімовірніша причина |
| --- | --- |
| Деплой впав на збірці | дивитись Logs; локально те саме перевіряє задача `docker` в CI |
| Сторінка відкрилась, але гра не під'єднується | проксі не пропускає `Upgrade` для `/ws`, або Origin не збігається — перевірити `/health` і консоль браузера |
| `/health` показує `sha: "dev"` | Render не передав `RENDER_GIT_COMMIT`; на роботу гри не впливає |
| Усе працює, але перший вхід довгий | сервіс спав, див. розділ вище |

## Варіант 2. Fly.io

Не засинає, але потребує CLI та картки при реєстрації.

```bash
brew install flyctl
flyctl auth signup                    # або flyctl auth login
flyctl launch --copy-config --no-deploy
flyctl secrets set ALLOWED_ORIGINS=https://starfall.fly.dev
flyctl deploy
```

Конфіг [`fly.toml`](../fly.toml) уже з вимкненим автозасинанням: для гри
холодний старт на першому гравцеві неприйнятний.

## Запасний план на день захисту

Якщо хостинг із якоїсь причини не піднявся, гру можна показати з власної
машини через тимчасовий тунель — обліковий запис не потрібен:

```bash
brew install cloudflared
npm start                                   # сервер на 8080
cloudflared tunnel --url http://localhost:8080
```

Команда надрукує адресу виду `https://щось-випадкове.trycloudflare.com`.
Вона вже з `https`, тому клієнт сам обере `wss://`. Перед запуском:

```bash
export ALLOWED_ORIGINS=https://щось-випадкове.trycloudflare.com
```

Чим це **не** є: постійним деплоєм. Адреса живе, поки запущена команда,
гра працює з вашого ноутбука, і трафік іде через вашу мережу. Для
демонстрації вистачає, для здачі «живої адреси» — ні.

## Чому не GitHub Pages

Pages віддає лише статику. Starfall — це процес, який рахує гру й тримає
WebSocket; від клієнта без сервера лишилося б порожнє лобі.
