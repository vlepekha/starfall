# Starfall — семестровий проєкт (лаби 01–03)

Мультиплеєрна браузерна гра в реальному часі. Тема — космічні кораблі.

| Тег | Лаба | Що додано |
| --- | --- | --- |
| `lab-01` | Event Loop & Game Loop | ігровий цикл із фіксованим кроком, корабель, три експерименти |
| `lab-02` | Objects, Prototypes & this | модель сутностей, кулі, астероїди, зіткнення, pickup, homing |
| `lab-03` | Async JavaScript | пайплайн ассетів, спрайтшити, звук, лобі, шина подій |

Нижче частини йдуть по порядку: цикл, сутності, асинхронність. Код лаби 1
нікуди не подівся: `integrate()` так само чиста функція, `createLoop()` так само
крутить 60 кроків/с — просто тепер цикл оновлює не один корабель, а цілий світ.

Стек: Vite (vanilla JS, ES-модулі), Canvas 2D, Biome (лінтер + форматер). Без залежностей у рантаймі.

# Частина 1 — Event Loop & Game Loop

Тег `lab-01`.

## Як влаштований цикл

`requestAnimationFrame` викликає нас із частотою монітора: 60, 120 або 144 рази на секунду.
Симуляція ж має йти **рівно 60 разів/с на будь-якому залізі**, інакше фізика
буде різною в різних гравців — а це вже мультиплеєр, якого в нас буде далі.

Тому час між кадрами складається в акумулятор і «з'їдається» цілими кроками:

```js
accumulator += Math.min(frameTime, MAX_FRAME_TIME);
while (accumulator >= dt) {
  update(dt);          // dt завжди 1/60, ніколи не змінюється
  accumulator -= dt;
}
render(accumulator / dt); // alpha ∈ [0,1) — де ми «між» двома станами
```

Три деталі, які легко пропустити:

1. **`Math.min(frameTime, MAX_FRAME_TIME)`** — захист від «спіралі смерті».
   Якщо вкладка була згорнута 10 секунд, без обмеження ми спробуємо зробити 600
   кроків в одному кадрі, кадр триватиме довше за наступний — і далі по спіралі.
   Кожне спрацювання рахується в `stats.panics`.
2. **Інтерполяція.** Симуляція «стрибає» 60 разів/с, монітор може малювати 144 рази/с.
   Без інтерполяції між двома станами рух помітно рваний. `render(alpha)` малює
   стан між попереднім і поточним кроком. Інтерполюються **і позиція, і кут**,
   причому обидва — найкоротшим шляхом: позиція по тору (інакше на межі арени
   корабель летів би через увесь екран), кут через нормалізацію різниці в межі
   ±π (інакше поворот через 180° давав би повний оберт назад за один кадр).
3. **`integrate()` нічого не знає про DOM.** Ні `performance.now()`, ні `Math.random()`,
   ні canvas. Той самий вхід → той самий вихід. Саме тому той самий файл згодом
   запуститься на сервері (Node) для звірки станів — і саме тому експеримент 3
   вимірюється в Node без браузера взагалі.

Затухання швидкості — `Math.exp(-damping * dt)`, а не `1 - k * dt`: експонента коректна
при будь-якому `dt`, а лінійна форма при великому `dt` дає від'ємний множник і корабель
починає летіти назад.

## Замикання: `createInput()`

Набір натиснутих клавіш живе всередині функції. Зовні його не видно й не змінити —
доступ тільки через повернені методи:

```js
export function createInput(target = window, bindings = DEFAULT_BINDINGS) {
  const pressed = new Set();          // ← у замиканні, приватний
  target.addEventListener("keydown", onKeyDown);
  return { snapshot, isDown, dispose };
}
```

`snapshot()` віддає простий незмінний об'єкт — один знімок на один крок симуляції.
Слухач `blur` обов'язковий: без нього після перемикання вкладки клавіша «залипає»
назавжди, бо `keyup` прилетить уже іншому вікну.

### Дія-стан і дія-подія

Тяга — це **стан**: поки клавішу тримають, прискорення діє щокроку. А перемкнути
щось треба **один раз на натискання**, скільки б кроків клавішу не тримали.
Браузер тут не допоможе: він шле `keydown` повторно з автоповтором, тому
«вперше» доводиться визначати самому — другий `Set`:

```js
const pressed = new Set();   // що утримується зараз
const fresh   = new Set();   // що натиснули саме на цьому кроці

onKeyDown: if (!pressed.has(action)) fresh.add(action); pressed.add(action);

isDown(action)      → pressed.has(action)
justPressed(action) → fresh.has(action)
endStep()           → fresh.clear()
```

`endStep()` викликається в кінці кожного кроку симуляції — «свіжі» натискання
живуть рівно один крок. Забути його означає, що `justPressed` залипне назавжди.

Перевірено на клавіші <kbd>V</kbd> (вмикає вектор швидкості): три `keydown`
підряд без `keyup` дають **одне** спрацювання, а не три.

> браузер тротлить `requestAnimationFrame` приблизно до 1 Гц — під час підготовки цієї
> лаби спроба зняти числа з фонової вкладки давала `frames/s = 1`. Це теж факт про
> event loop: rAF прив'язаний до малювання, а не до плину часу.

Найважливіше в таблиці — **колонка `steps/s`: у всіх чотирьох режимах вона дорівнює 60**.
Саме це й мав забезпечити фіксований крок. Усе інше — те, що навколо нього ламається.

### Експеримент 1 — блокуючий цикл у кадрі

**Що ламаємо.** У `render()` додається синхронний цикл `burnMilliseconds(N)`, який
крутиться в `while` доти, доки не мине N мілісекунд.

**Що очікуємо.** `frame time` зросте рівно на N. Поки цей цикл виконується, стек
викликів зайнятий: браузер не може ні намалювати кадр, ні обробити `keydown`,
ні виконати мікрозадачу. Якщо N > 16.7 мс, кадр не встигає до наступного vsync,
і `frames/s` падає приблизно до `1000 / (N + власний час кадру)`.

**Виміряно.** `frame time` 0.30 → 20.00 мс, тобто рівно +20 мс, які ми самі й спалили.
`frames/s` 61 → 50: це `1000 / 20` — кадр більше не встигає до vsync, і монітор показує
кожен другий. Картинка помітно смикається.

**Чому `steps/s` лишилося рівно 60.** Пропущений час нікуди не зникає —
він осідає в акумуляторі, і наступний кадр робить не один крок, а два-три поспіль.
Це видно й у HUD: `accumulator` у момент заміру показував 13.70 мс проти 3.70 —
майже цілий крок чекає на наступний кадр. Симуляція йде в темпі 60 кроків/с навіть тоді, коли картинка
вже смикається. Це і є головна перевага фіксованого кроку: падає плавність, а не сама гра.
На великих N видно, як росте `panics` — спрацьовує обмеження `MAX_FRAME_TIME`.

**Висновок.** Будь-яка синхронна робота в кадрі — це прямий мінус до FPS, один в один.
Важкі обчислення в реальній грі йдуть або у Web Worker (окремий потік, свій event loop),
або розбиваються на порції між кадрами.

### Експеримент 2 — `setInterval(16)` замість `requestAnimationFrame`

**Що ламаємо.** `createIntervalLoop()` у `src/engine/loop-variants.js` планує тік через
`setInterval(tick, 16)` замість rAF.

**Що очікуємо.** `frames/s` не дорівнює частоті монітора: `setInterval` кладе колбек
у **task queue** через приблизно 16 мс, а це число не має нічого спільного з моментом,
коли браузер збирається малювати (16.67 мс при 60 Гц, 6.94 мс при 144 Гц). Фази
розходяться, і з'являються два дефекти:

- **дубльовані й пропущені кадри** — між двома vsync інколи трапляється два тіки,
  інколи жодного; на екрані це мікро-ривки навіть при гарному `frames/s` у HUD;
- **фаза, що постійно повзе** — 16 ≠ 16.67, тож тіки поступово зсуваються відносно
  моменту малювання; до того ж `setInterval` гарантує «не раніше ніж», а не «рівно через»,
  тому реальний інтервал ще й плаває.

**Виміряно.** `frames/s` = **63** при дисплеї 60 Гц — це рівно `1000 / 16`, тобто темп
таймера, а не екрана. Три «кадри» на секунду намальовано в нікуди: монітор фізично не
може показати більше за 60, тож частина роботи щоразу викидається. Формально число
в HUD навіть «краще» за baseline (61) — насправді це прямий доказ того, що цикл живе
власним життям і на екран не дивиться. Саме тут видно різницю між «полічили кадр»
і «показали кадр».

`accumulator` у цьому режимі показував 9.30 мс проти 3.70 у baseline, але сюди читати
дрейф не варто: це миттєвий знімок залишку, і він залежить від того, в якій фазі
застав його замір. Надійний сигнал — саме 63 ≠ 60.

Плюс `setInterval` продовжує тікати у фоновій вкладці (браузер душить його до 1 Гц),
тоді як rAF просто чесно зупиняється до повернення вкладки.

**Висновок.** rAF — єдиний таймер, синхронізований із малюванням. Для рендера
альтернатив немає. Для мережі й логіки, навпаки, таймер доречний: rAF там зайвий,
бо він зупиниться у фоні разом із вкладкою.

### Експеримент 3 — змінний крок замість фіксованого

**Що ламаємо.** `createVariableLoop()` передає в `update()` реальний час кадру,
акумулятора немає взагалі.

**Виміряно — і саме тут заміри нічого не показують.** 60 steps/s, 60 frames/s,
`accumulator` = 0.00, frame time навіть трохи менший за baseline (немає роботи
з акумулятором). У браузері цей режим виглядає **бездоганно**, і в цьому вся пастка:
на одній машині зламаного нічого не видно. Дефект проявляється тільки при порівнянні
двох різних машин — або при порівнянні клієнта з сервером.

Тому цей експеримент міряється в Node, без браузера: `integrate()` — чиста функція,
тож результат не залежить від заліза й відтворюється будь-ким.

```bash
npm run bench:physics
```

Тримаємо «вправо + тяга» 10 секунд модельного часу, порівнюємо кінцеву позицію:

| Схема кроку | x | y | відхилення від еталона, од. |
| --- | ---: | ---: | ---: |
| фіксований 60 Гц (еталон) | 1284.6 | 481.9 | 0.0 |
| фіксований 60 Гц, повтор | 1284.6 | 481.9 | 0.0 |
| акумулятор, рендер 144 Гц | 1285.5 | 482.0 | 1.0 |
| акумулятор, рендер 30 Гц ±40% jitter | 1284.6 | 481.9 | 0.0 |
| змінний крок @144 Гц | 1285.6 | 470.1 | **11.9** |
| змінний крок @60 Гц | 1284.6 | 481.9 | 0.0 |
| змінний крок @30 Гц | 1282.3 | 502.1 | **20.3** |
| змінний крок @60 Гц ±30% jitter | 1283.3 | 481.3 | **1.4** |
| змінний крок @60 Гц ±30% jitter, інший seed | 1285.3 | 481.5 | **0.9** |

Читається так: з акумулятором частота рендера на траєкторію не впливає — 30 Гц із
дрижанням дає біт у біт ту саму позицію, що й еталон. Зі змінним кроком гравець зі
144-герцовим монітором за 10 секунд опиняється на 12 одиниць далі, ніж гравець із
60 Гц, а з 30 Гц — на 20 одиниць. Причина — помилка чисельного інтегрування: при
більшому `dt` метод Ейлера систематично зрізає криву.

(Рядок «акумулятор, рендер 144 Гц» дає 1.0 не через недетермінізм, а через хвіст:
на момент зупинки в акумуляторі лишився неспожитий залишок, тобто зроблено на один
крок менше. Ця одиниця — рівно один крок симуляції, а не розбіжність.)

Друга частина експерименту — тунелювання:

```
Тунелювання: стіна на x=200, швидкість 700 од./с.
Фіксований крок 1/60: перетин зафіксовано на кроці #17 — у корабля було 17 проміжних позицій до стіни.
Один кадр dt=0.5 c — корабель одразу в x=330: стіну пройдено без жодної проміжної перевірки.
```

Один підвислий кадр (перемикання вкладки, GC, важкий `fetch`) — і об'єкт перестрибує
перешкоду. З фіксованим кроком такий «стрибок» розкладається на 30 кроків по 1/60,
і колізія неминуче знаходиться.

**Висновок.** Змінний крок недетермінований за побудовою: симуляція стає функцією
від частоти монітора й випадкових лагів. Для одиночної анімації це терпимо, для
мультиплеєра — ні: клієнт і сервер розійдуться на першому ж лагу.

## Порядок черг: перевірка в консолі

`src/main.js` друкує при старті:

```
1 sync
2 sync
3 microtask (queueMicrotask)
3.1 microtask (Promise)
4 macrotask (setTimeout)
5 rAF (before paint)
```

Порядок такий і є: спершу до кінця виконується синхронний код (`1`, `2`), потім
**повністю** спорожнюється черга мікрозадач (`3`, `3.1`) — обидві, і `queueMicrotask`,
і `.then()`, ідуть в одну чергу, — і тільки після цього береться **одна** макрозадача (`4`).
`rAF` (`5`) — не макрозадача й не мікрозадача: його колбеки виконуються окремою фазою
перед малюванням кадру, тому він тут останній.

## Reflection (частина 1)

**Чому симуляція фіксована, а рендер — ні?**
Фізика має бути однаковою у всіх гравців, тому її крок — константа `1/60`.
Рендер же має відповідати можливостям конкретного екрана: 144 Гц монітор має право
малювати 144 кадри, просто 84 з них будуть інтерпольованими між станами симуляції.

**Що станеться, якщо прибрати `Math.min(frameTime, MAX_FRAME_TIME)`?**
Після повернення з фонової вкладки акумулятор міститиме секунди. Один кадр спробує
зробити сотні кроків, займе більше часу, ніж симулює, — акумулятор за цей час виросте
ще сильніше. Це «спіраль смерті»: вкладка зависає остаточно.

**Навіщо `alpha` в `render()`, якщо без нього все й так рухається?**
Без інтерполяції на 144 Гц кожен третій кадр показує той самий стан симуляції —
рух виглядає ривками з періодом 60 Гц. `alpha` — частка кроку, яка вже «набігла»
в акумуляторі; вона перетворює 60 дискретних станів на неперервний рух.

**Чому `integrate()` не має права викликати `Math.random()` або `performance.now()`?**
Бо тоді вона перестає бути чистою, а разом із цим гине детермінізм. Для наступних
лаб (мережа, звірка станів клієнта й сервера) потрібно, щоб той самий вхід завжди
давав той самий вихід — інакше нічого звіряти.

**Чому `setInterval` не годиться для рендера, але годиться для мережі?**
rAF синхронізований із малюванням і зупиняється у фоні — це те, що треба для картинки,
і те, чого не можна допустити для мережевого тіку. Мережа має продовжувати працювати,
навіть коли вкладка не на екрані.

# Частина 2 — Об'єкти, прототипи та `this`

Тег `lab-02`. До корабля з лаби 1 додалися кулі, астероїди, підбирані бонуси,
зіткнення, вибухи, рахунок і респаун. Керування: <kbd>Space</kbd> — вогонь.

## Модель сутностей

Три рівні, і жодного зайвого:

```
Vector2           незмінне значення (позиція, швидкість)
Entity            усе, що живе на арені: id, position, velocity, radius, kind
  └── Ship / Bullet / Asteroid / Pickup / Particle     ← рівно один рівень
behaviors[]       композиція: ttl, homing, pickup, spin
```

### `Vector2` — чисті методи

Жоден метод не чіпає ні `this`, ні аргумент: усі повертають **новий** вектор.
Конструктор ще й викликає `Object.freeze(this)`, тож спроба `v.x = 99`
у strict mode (а модулі завжди strict) кидає `TypeError`.

```js
const a = new Vector2(3, 4);
const b = a.add(new Vector2(1, 1)); // a лишився (3, 4)
a.x = 99;                           // TypeError: Cannot assign to read only property
```

Ціна — зайві об'єкти на кожен крок. При 40–60 сутностях це ніщо; коли
дійде до оптимізації під GC (лаба 7), саме тут буде перший кандидат на зміни.

### `Entity` і приватний лічильник

```js
export class Entity {
  static #nextId = 1;        // приватне статичне поле
  constructor({ ... }) {
    this.id = Entity.#nextId++;
  }
}
```

`#nextId` недосяжний ззовні взагалі: ні через `Entity.#nextId`, ні через
прототип, ні через `Object.keys`. Це не домовленість на кшталт `_nextId`,
а синтаксична заборона — звернення ззовні не компілюється.

### `Ship`: приватне `#hp` і публічний `get hp()`

```js
class Ship extends Entity {
  #hp;
  get hp() { return this.#hp; }
  damage(amount, world) { ...; if (this.#hp === 0) world.emit("death", ...); }
}
```

Зовні здоров'я читається, але не записується. Перевірено: `ship.hp = 99`
кидає `TypeError`, бо є тільки getter. Сенс не в «інкапсуляції заради
інкапсуляції»: будь-яка зміна HP зобов'язана пройти через `damage()`,
який уміє помітити нуль і повідомити світ про смерть. З публічним полем
хтось рано чи пізно написав би `ship.hp -= 1` — і корабель їздив би
з від'ємним здоров'ям, бо подію смерті ніхто не надіслав би.

### `World` поверх `Map<id, Entity>`

Чому `Map`, а не масив чи звичайний об'єкт:

- ключі лишаються числами (у звичайному об'єкті вони стали б рядками);
- видалення за id — O(1), без пошуку по масиву;
- порядок вставки збережений, тож ітерація детермінована — а від порядку
  залежить розбір зіткнень.

Порядок усередині `World.step(dt)` має значення:

```js
step(dt) {
  for (const e of this.#entities.values()) { e.previousPosition = e.position; e.update(dt, this); }
  this.stats.collisions = resolveCollisions(this);  // по НОВИХ позиціях
  for (const e of this.#spawnQueue) this.#entities.set(e.id, e);
  this.#sweep();                                     // мертвих прибираємо в кінці
}
```

Дві пастки, на які це наступає навмисно:

1. **Народження відкладене.** Додавати в `Map` під час ітерації по ній — шлях
   до нескінченного циклу: куля породжує кулю породжує кулю. Тому все нове
   чекає в черзі до кінця кроку.
2. **Смерть — це позначка, а не видалення.** `kill()` ставить `alive = false`,
   а `#sweep()` викидає такі записи рівно один раз, наприкінці кроку. Якби
   сутність зникала одразу, куля встигла б щезнути до того, як система
   зіткнень дійшла б до неї.

Ітерація — через `Symbol.iterator`, вибірка за видом — через генератор:

```js
*ofKind(kind) {
  for (const entity of this.#entities.values()) {
    if (entity.kind === kind && entity.alive) yield entity;
  }
}
```

Генератор тут не прикраса: `homing` щокроку шукає найближчий астероїд і
зупиняється, щойно знайшов. Проміжний масив довелося б створювати
60 разів на секунду на кожну самонавідну кулю.

### Зіткнення

Наївний перебір пар, коло-коло, O(n²). При 60 сутностях це ~1800 перевірок
на крок — частки мілісекунди. Просторове розбиття було б передчасною
оптимізацією; його місце в лабі 7, коли з'являться боти й навантаження.

Важливо інше: **система зіткнень не знає, що робити при зіткненні**. Вона
знаходить пари й питає таблицю правил:

```js
defineCollision("bullet", "asteroid", (bullet, asteroid, world) => { ... });
defineCollision("ship",   "pickup",   (ship, item, world) => { ... });
```

Додати новий вид сутності — це рядок у `rules.js`, а не правка перебору.
Відстань рахується по тору (`wrappedDistanceTo`), інакше через край
нічого не влучало б.

### Рендер астероїдів

Кожен камінь — процедурний спрайт: силует із двох «октав» шуму, кратери
з чашею й валом, тріщини, мікрорельєф, крап, термінатор і освітлений край.
Усе це малюється **один раз** в офскрін-канвас при появі астероїда й кешується
в `Map` за ключем `id:радіус:вид`; кадр лише повертає готову картинку.

Так деталізація перестає коштувати часу кадру: при 20 сутностях frame time
лишається **0.40 мс** — рівно стільки ж, скільки було з примітивним
многокутником. Форма детермінована від `id`, тому камінь не «кипить»
між кадрами й упізнається від появи до розпаду.

Палітри розділяють два кольори: `tint` — лише для освітленого краю силуету,
`surface` — для кратерів і крапу. Якщо фарбувати поверхню кольором підсвітки,
камінь стає рівномірно забарвленим і втрачає матеріальність; найпомітніше
це було на астероїді-мисливці, який через це виглядав просто рожевою плямою.

## Баг із `this`

У шапці є кнопка **Fire** і прапорець **«зламаний this»**. З прапорцем
кнопка робить рівно те, що хочеться написати першим:

```js
fireButton.addEventListener("click", game.ship.fire);   // ← так не працює
```

Виміряно, не припущено — ось що друкує сторінка:

```
this зламався — TypeError: Cannot read private member #fireCooldown
from an object whose class did not declare it
```

А ось те саме з голим викликом (`src/game/this-demo.js`, друкується в консоль
при старті):

```
2. const f = ship.fire; f() -> TypeError: Cannot read properties of undefined (reading '#fireCooldown')
```

**Чому так.** `ship.fire` — це просто посилання на функцію. Воно не тягне за
собою об'єкт: прив'язка `this` у JS відбувається **в момент виклику**, а не
в момент отримання методу. Далі працює одне з чотирьох правил:

| Як викликали | Чим буде `this` |
| --- | --- |
| `ship.fire(world)` | `ship` — об'єкт зліва від крапки |
| `const f = ship.fire; f()` | `undefined` (модулі завжди в strict mode) |
| `f.call(obj)` / `f.bind(obj)()` | те, що передали явно |
| `new Ship()` | новий екземпляр |

У випадку з `addEventListener` спрацьовує третє правило: DOM викликає слухач
із `this === currentTarget`, тобто кнопкою. Кнопка — не `Ship`, у неї немає
приватного поля `#fireCooldown`, звідси й повідомлення «from an object whose
class did not declare it». Зверніть увагу, яке саме це повідомлення: приватні
поля ловлять таку помилку **жорсткіше**, ніж звичайні. Якби `fireCooldown`
був публічним, `this.fireCooldown` на кнопці повернув би `undefined`,
`undefined > 0` дало б `false` — і постріл «відбувся» б у порожнечу,
мовчки, без жодної помилки. Приватне поле падає одразу й голосно.

### Три способи полагодити

```js
// 1. стрілка — не має власного this, бере його із замикання (обрано)
fireButton.addEventListener("click", () => game.ship.fire(game.world));

// 2. bind — прив'язує this назавжди, повертає нову функцію
fireButton.addEventListener("click", game.ship.fire.bind(game.ship, game.world));

// 3. поле-стрілка в класі — this прив'язується при створенні екземпляра
class Ship extends Entity {
  fire = (world) => { ... };
}
```

**Чому обрано перший.** Стрілка найдешевша для читання: видно і об'єкт,
і аргументи. `bind` створює нову функцію, тому її не можна зняти через
`removeEventListener`, не зберігши посилання — класичне джерело витоків
слухачів. Третій варіант кладе функцію **в кожен екземпляр** замість
прототипу: 100 кораблів — 100 копій функції, і метод зникає з
`Ship.prototype`, тобто його не перевизначити в нащадку.

У грі є й четвертий, найголовніший фікс — **не передавати метод узагалі**.
Корабель не підписаний на клавіатуру; йому дали функцію-джерело вводу:

```js
game.ship.controller = () => input.snapshot();
```

Тепер `Ship` не знає ні про DOM, ні про клавіші. У лабі 5 на це місце
стане мережевий пакет або бот — і в класі не зміниться жодного рядка.

## Експеримент: ланцюжок прототипів

`src/game/this-demo.js` друкує в консоль при кожному запуску:

```
Ship (екземпляр) -> Ship -> Entity -> Object
ship instanceof Ship: true
власні ключі екземпляра: id, position, velocity, radius, kind, angle, alive,
                         behaviors, previousPosition, fireInterval, thrusting,
                         invulnerableFor, controller
методи (update, fire, damage) лежать у Ship.prototype, а не в екземплярі
```

Що з цього видно:

- `class` — це синтаксис поверх прототипів, а не окремий механізм. `extends`
  просто ставить `Entity.prototype` у ланцюжок `Ship.prototype`.
- В екземплярі лежать **лише дані**. Методи — один раз у прототипі, спільні
  для всіх кораблів. Тому `fire = () => {}` як поле класу і був би
  витратним: він поклав би функцію в кожен екземпляр.
- `#hp` у списку власних ключів **немає** — приватні поля не видно ні через
  `Object.keys`, ні через `JSON.stringify`, ні в дебагері як звичайну властивість.

## Дизайн-запис: чому композиція, а не ієрархія

Дві фічі, які мали зламати дерево класів: **homing** (самонаведення) і
**pickup** (підбиране).

### Як виглядала б ієрархія

Homing треба і кулі, і астероїду-мисливцю. Через успадкування:

```
Entity
├── Bullet
│   ├── PlainBullet
│   └── HomingBullet        ← логіка наведення
└── Asteroid
    ├── PlainAsteroid
    └── HuntingAsteroid     ← ТА САМА логіка наведення
```

Код наведення доводиться або дублювати в двох гілках, або піднімати
в `Entity` — тобто давати його всьому на світі, включно з частинками вибуху.
Далі стає гірше. Знадобилася самонавідна куля, яка ще й вибухає — потрібен
`ExplodingHomingBullet`. Мисливець, що розпадається — `SplittingHuntingAsteroid`.
Кожна нова незалежна властивість **множить** кількість класів, а не додає один.

Pickup ламає дерево з іншого боку. Він стоїть на місці, має радіус,
бере участь у зіткненнях, але не корабель, не куля і не перешкода. У дереві
це або ще одне відгалуження від `Entity`, або — що гірше — `Pickup extends Ship`
«бо в нього теж є HP і колізія». Другий варіант виглядає зручним рівно до
моменту, коли pickup успадкує `fire()` і зможе стріляти.

### Як зроблено

Поведінка — звичайний об'єкт з `update(entity, dt, world)`:

```js
export function homing({ targetKind, turnRate, range }) {
  return {
    name: "homing",
    update(entity, dt, world) {
      const target = world.nearestOfKind(targetKind, entity.position, range);
      if (!target) return;
      // довернути velocity до цілі, модуль швидкості зберегти
    },
  };
}
```

Причіпляється до чого завгодно:

```js
Bullet.homing(...)    → behaviors: ttl, homing
Asteroid.hunter(...)  → behaviors: spin, homing
```

Це **різні класи без спільного предка, крім `Entity`** — і однаковий код
наведення, написаний один раз. Pickup так само: клас тримає тільки дані
(позиція, радіус, підпис), а ефект — функція всередині поведінки:

```js
Pickup.repair(position)      // effect: (ship) => ship.heal(1)
Pickup.homingAmmo(position)  // effect: (ship) => { ship.homingShots += 12 }
```

Нові бонуси — нові функції, **нуль нових класів**.

### Що це дало і чим коштувало

| | Ієрархія | Композиція |
| --- | --- | --- |
| Куля + астероїд з наведенням | 2 класи з дублем коду | 1 функція на обох |
| Нова незалежна властивість | множить класи | +1 рядок у `behaviors` |
| Поведінка під час гри | не змінити | `behaviors.push(...)` будь-коли |
| Де шукати логіку сутності | один клас — видно все | розкидано по поведінках |
| Порядок виконання | очевидний | залежить від порядку в масиві |

Ціна чесна: читаючи `class Asteroid`, ви **не бачите**, що конкретний
екземпляр самонавідний — це видно лише в його `behaviors`. Налагоджувати
трохи важче, і порядок поведінок у масиві значущий (наведення має
відпрацювати до руху, інакше швидкість застосується на крок пізніше).

Для гри цей обмін вигідний: незалежних властивостей буде багато
(щити, прискорювачі, різні боєприпаси), і кожна з них має комбінуватися
з рештою. Саме комбінаторика й вбиває дерево класів.

Успадкування лишили там, де воно справді про «різновид»: `Ship`, `Bullet`,
`Asteroid` — це дійсно різні **види** сутностей із різним малюванням і
різною роллю в зіткненнях. Але рівно один рівень углиб.

## Reflection (частина 2)

**Чому `#hp` приватне, а `hp` — лише getter?**
Щоб будь-яка зміна здоров'я проходила через `damage()`, який уміє помітити
нуль і надіслати подію смерті. Публічне поле дозволило б `ship.hp -= 1`
в обхід цієї логіки — і корабель жив би з нульовим HP.

**Чому мертві прибираються в кінці кроку, а не одразу?**
Бо під час розбору зіткнень список уже ітерується. Видалення посеред
ітерації або зламає перебір, або дасть ефект «куля зникла раніше, ніж
влучила». Позначка `alive = false` плюс `#sweep()` наприкінці — це одна
точка видалення й передбачуваний порядок.

**У чому різниця між `ship.fire` і `ship.fire.bind(ship)`?**
Перше — посилання на функцію без будь-якої прив'язки: `this` визначиться
в момент виклику й буде `undefined` або елементом DOM. Друге — **нова**
функція з назавжди прив'язаним `this`. Саме тому її не можна зняти через
`removeEventListener`, не зберігши посилання.

**Чому `Map`, а не масив сутностей?**
Видалення за id за O(1) і числові ключі. У звичайному об'єкті `{1: entity}`
ключ став би рядком `"1"`, і `world[entity.id]` поводився б несподівано.
Масив дав би O(n) на кожне видалення — а видаляємо ми щокроку.

**Де тут прототипи, якщо скрізь `class`?**
`class` — синтаксис поверх них. Методи лежать у `Ship.prototype`, екземпляр
тримає лише дані, а `extends` вибудовує ланцюжок
`ship → Ship.prototype → Entity.prototype → Object.prototype`. Це видно
в консолі при кожному запуску.

**Що станеться, якщо homing додати і кулі, і астероїду одночасно?**
Нічого особливого — саме для цього композиція й потрібна. Два різні класи
отримують ту саму функцію наведення; вона працює з `entity.velocity`
і не питає, ким цей entity є.

# Частина 3 — Асинхронний JavaScript

Тег `lab-03`. Гра більше не починається одразу: спершу вантажаться ассети
зі справжнім прогрес-баром, потім лобі з вибором кімнати, і лише після
«Join» — арена. Кораблі, кулі й астероїди тепер зі спрайтшитів, постріли
й вибухи звучать.

## Пайплайн ассетів

`public/assets/manifest.json` описує все, що треба завантажити:

```json
{
  "images": [{ "id": "ships", "url": "/assets/ships.png",
               "frameWidth": 96, "frameHeight": 64, "frames": 4,
               "originX": 58, "originY": 32 }],
  "audio":  [{ "id": "fire", "url": "/assets/sfx-fire.wav" }],
  "data":   [{ "id": "arena", "url": "/assets/arena.json" }]
}
```

Три завантажувачі з одним спільним ядром:

```js
export async function fetchChecked(url, { signal }) {
  const response = await fetch(url, { signal });
  // fetch НЕ кидає на 404 — він спокійно віддає ok: false.
  if (!response.ok) throw new HttpError(response.status, url);
  return response;
}
```

Це не формальність. Забути `response.ok` означає отримати на 404 не
«файлу немає», а «SyntaxError: Unexpected token <» десь у надрах
`JSON.parse` — і півгодини шукати, де ж поділися дані.

**Картинка вантажиться через `fetch` + `createImageBitmap`, а не `new Image()`.**
У `<img>` немає ні `AbortSignal`, ні коду помилки: лише подія `error` без
жодних подробиць. З `fetch` ми розрізняємо 404 і обрив мережі, і вміємо
скасувати завантаження.

### Повтори: backoff із джитером, але не на 4xx

```js
export function backoffDelay(attempt, base = 220, cap = 4000) {
  const exponential = Math.min(cap, base * 2 ** attempt);
  const jitter = exponential * (Math.random() - 0.5);  // ±50%
  return Math.round(exponential + jitter);
}
```

Джитер тут не для краси. Без нього всі клієнти, що впали разом, повторять
запит теж разом — і покладуть сервер удруге. Випадковий розкид розводить
їх у часі.

Що повторюємо, а що ні:

| Ситуація | Повтор | Чому |
| --- | --- | --- |
| 404, 403 | **ні** | «файлу немає» не мине саме собою — користувач чекатиме дарма |
| 500, 502 | так | сервер може оговтатися |
| обрив мережі (`TypeError`) | так | класична тимчасова проблема |
| таймаут | так | повільна мережа часто відпускає |
| наш `abort()` | **ні** | це не збій, а свідомий вихід |

Таймаут власний на **кожну спробу**, а не один на всі:

```js
function attemptSignal({ signal, timeout }) {
  const timer = AbortSignal.timeout(timeout);
  return signal ? AbortSignal.any([signal, timer]) : timer;
}
```

Якби сигнал створювався один раз зовні, друга спроба стартувала б із уже
вичерпаним лімітом часу й падала миттєво.

## Sequential vs concurrent — заміряно

Обидва шляхи реалізовані: `loadAll()` через `Promise.all` і
`loadAllSequential()` через `await` у циклі. Другий існує рівно заради
цього заміру.

Умови: Chrome 152, dev-сервер Vite на localhost, 7 файлів (3 PNG, 3 WAV,
1 JSON), медіана з трьох прогонів, кожен файл із унікальним query-параметром,
щоб кеш не псував результат.

| Умови | Послідовно | Паралельно | Різниця |
| --- | ---: | ---: | ---: |
| localhost, без затримки | 35.0 мс | **7.2 мс** | 4.9× |
| +120 мс затримки на файл | 890.7 мс | **256.9 мс** | 3.5× |

Другий рядок цікавіший. 7 файлів × 120 мс = 840 мс — рівно те, що показує
послідовний варіант: він **додає** затримки одна до одної. Паралельний
укладається в ~257 мс, тобто приблизно в одну затримку плюс передачу даних:
усі сім запитів чекають одночасно.

Різниця в 3.5× тут узята на localhost. У реальній мережі з RTT 50–100 мс
на кожен файл розрив лише росте — і це при тому, що браузер усе одно
обмежує кількість одночасних з'єднань до одного хоста.

```js
const settled = await Promise.all(tasks);
```

Нюанс, про який легко забути: `Promise.all` відхиляється на **першій**
помилці, але решта запитів продовжують летіти — проміси не скасовуються
самі. Саме тому зовні стоїть `AbortController`: після збою ми обриваємо
все, що ще не встигло.

Чому не `allSettled`: гра не може стартувати без спрайтів. «Частково
завантажилось» — не той випадок, коли варто продовжувати; чесніше
зупинитися й показати Retry.

## Спрайти й звук

`npm run assets` генерує все в `public/assets`:

| Файл | Що всередині |
| --- | --- |
| `ships.png` | 4 кадри 96×64: без тяги, тяга слабка, тяга повна, урон |
| `asteroids.png` | 6 кадрів 128×128: 4 звичайні камені + 2 мисливці |
| `bullets.png` | 2 кадри 24×24: звичайна куля й самонавідна |
| `sfx-*.wav` | постріл, влучання, вибух |

Ассети **генеруються**, а не лежать готовими: у репозиторії немає бінарників
невідомого походження, а будь-який спрайт відтворюється однією командою.
У Node немає canvas, тому в `tools/` є мінімальний растеризатор
(`raster.mjs`), кодувальник PNG на `zlib` (`png.mjs`) і кодувальник
WAV (`wav.mjs`). Процедурна генерація каменів, що в лабі 2 працювала
в рантаймі, переїхала сюди — тепер вона запікається офлайн.

Кадр корабля навмисно не квадратний (96×64): полум'я тягнеться назад далеко
за силует, і в квадраті 64×64 його просто обрізало б. Тому в маніфесті є
`originX`/`originY` — точка, навколо якої спрайт обертається.

### Web Audio

Два правила, які не обійти:

1. **`AudioContext` не запуститься без жесту користувача.** Браузери
   блокують автовідтворення, тому контекст створюється на кліку «Join» —
   це єдиний момент, коли така нагода є. Створити його на завантаженні
   сторінки означає отримати `state: "suspended"` і тишу.
2. **`decodeAudioData` асинхронне й важке.** Декодуємо один раз на етапі
   завантаження, а не під час пострілу — інакше перший постріл дав би
   просідання кадру.

Звуки, що приїхали до розблокування контексту, лежать сирими байтами
й декодуються всі разом у момент `unlock()`.

## Шина подій: sim нічого не знає про звук

Вимога «сим не імпортує audio.js / HUD» вирішена через `EventTarget`:

```js
export class GameBus extends EventTarget {
  emit(type, detail = {}) {
    this.dispatchEvent(new CustomEvent(type, { detail }));
  }
}
```

`World` отримує шину в конструкторі й лише кидає в неї події — `fired`,
`hit`, `exploded`, `score`, `pickup`. Хто підписався, його не стосується:

```js
bus.on("fired",    () => play("fire"),    { signal });
bus.on("exploded", ({ big }) => play("explode", { gain: big ? 1 : 0.55 }), { signal });
```

Приберіть `audio/` з проєкту — симуляція не помітить. Перевірка проста:
у `src/sim/` немає жодного імпорту з `audio/` чи `render/`.

`EventTarget` узятий не для краси: він приймає `AbortSignal`, тож усі
підписки знімаються одним `abort()` без ручного обліку слухачів.

## Лобі

`class Lobby extends EventTarget` опитує `GET /api/rooms`, поки лобі видиме.
У самому класі **немає жодного звернення до `document`** — за розмітку
відповідає `lobby-dom.js`. Тому логіку опитування можна перевірити в Node,
а UI замінити, не чіпаючи мережу.

```js
const signal = AbortSignal.any([
  this.#controller.signal,      // гравець вийшов із лобі
  AbortSignal.timeout(2500),    // сервер не відповідає
]);
```

Два різні приводи зупинити запит зводяться до одного сигналу. У `catch`
вони розрізняються: `AbortError` — це нормальний вихід, його мовчки
ігноруємо; `TimeoutError` — показуємо «сервер не відповів вчасно».

`stop()` викликається при «Join» і обриває запит, що летить. Без цього
відповідь прийшла б уже під час гри й оновила б список кімнат, якого
на екрані немає.

У лабі 4 `/api/rooms` стане справжнім сервером; поки це middleware
у `vite.config.js` на 30 рядків.

## Головоломки порядку виконання

Запуск: `http://localhost:5273/?puzzles=1`, вивід у консолі. Головоломки
йдуть по черзі — якби вони стартували разом, їхні колбеки перемішалися б
в одних і тих самих чергах.

### 1. Базовий порядок

```js
console.log("A sync");
setTimeout(() => console.log("D setTimeout"), 0);
Promise.resolve().then(() => console.log("C microtask"));
console.log("B sync");
```

```
A sync → B sync → C microtask → D setTimeout
```

Синхронний код доходить до кінця, тоді черга мікрозадач, і лише потім
макрозадача. `setTimeout(…, 0)` означає «не раніше ніж за 0 мс», а не «зараз».

### 2. `await` — це `.then`

```js
console.log("A sync (до await)");
await null;                       // навіть не-проміс!
console.log("C після await");
```

```
A sync (до await) → C після await — мікрозадача
```

`await null` все одно відкладає продовження в чергу мікрозадач. Код після
`await` — це колбек, а не продовження того самого синхронного блоку.

### 3. `setTimeout` усередині `.then`

```js
Promise.resolve()
  .then(() => { console.log("B microtask"); setTimeout(() => console.log("E"), 0); })
  .then(() => console.log("C другий .then"));
setTimeout(() => console.log("D"), 0);
console.log("A sync");
```

```
A sync → B microtask → C другий .then → D setTimeout із синхронного коду
       → E setTimeout із мікрозадачі
```

Найцікавіше — хвіст. `E` заплановано **раніше** за `C`, але виконується
**останнім**: мікрозадача лише ставить макрозадачу в кінець черги задач,
де вже стоїть `D`. Таймери не «обганяють» один одного за часом створення.

### 4. `requestAnimationFrame` — окрема фаза

```js
requestAnimationFrame(() => { console.log("D rAF"); Promise.resolve().then(() => console.log("E")); });
setTimeout(() => console.log("C setTimeout 0"), 0);
queueMicrotask(() => console.log("B мікрозадача"));
console.log("A sync");
```

```
A sync → B мікрозадача → C setTimeout 0 → D rAF (перед малюванням)
       → E мікрозадача всередині rAF
```

`rAF` — не макрозадача й не мікрозадача: його колбеки виконуються окремою
фазою перед малюванням кадру. Тут він опинився **після** `setTimeout(0)`,
бо наступний кадр був ще не скоро; на зайнятій сторінці порядок цих двох
може помінятися — на відміну від решти рядків, які фіксовані специфікацією.
І зверніть увагу на `E`: черга мікрозадач спорожнюється і після rAF-колбеку теж.

### 5. Мікрозадачі, що породжують мікрозадачі

```js
setTimeout(() => console.log("E setTimeout"), 0);
Promise.resolve().then(() => {
  console.log("B мікрозадача 1");
  Promise.resolve().then(() => {
    console.log("C мікрозадача 2");
    Promise.resolve().then(() => console.log("D мікрозадача 3"));
  });
});
console.log("A sync");
```

```
A sync → B мікрозадача 1 → C мікрозадача 2 → D мікрозадача 3 → E setTimeout
```

Черга мікрозадач спорожнюється **повністю**, включно з тими, що додалися
під час її обробки. `E` чекає всіх трьох. Звідси ж і спосіб підвісити
вкладку назавжди: мікрозадача, яка нескінченно планує саму себе, не дасть
виконатися жодній макрозадачі й жодному кадру.

## Галерея збоїв

Кожен сценарій відтворюється адресою — ніякого «уявіть собі». Усі перевірені,
нижче справжній текст, який бачить гравець.

| Адреса | Що ламаємо | Поведінка | Що показує гра |
| --- | --- | --- | --- |
| `?fail=sprite-404` | `ships.png` → неіснуючий файл | **без повторів**, одразу Retry | `HTTP 404 — /assets/ships-missing.png` |
| `?fail=timeout` | `asteroids.png` віддається 8 с | 3 спроби по 2.5 с, тоді Retry | `сервер не відповів` |
| `?fail=abort` | `abort()` через 400 мс | тихо зупиняється, Retry | `завантаження перервано` |
| `?fail=broken-json` | `arena.json` → обірваний JSON | **без повторів** (це не мережа) | `Expected double-quoted property name in JSON at position 23` |
| `?fail=flaky-5xx` | `bullets.png` → 500 двічі | 2 повтори, далі **успіх** | `повтор bullets: спроба 1 через 294 мс`, `спроба 2 через 364 мс` |

У жодному з п'яти випадків сторінка не падає: гра або стартує (останній
рядок), або показує причину й кнопку **Retry завантаження**. Прогрес-бар
при збої стає червоним, список файлів лишається на екрані — видно, що саме
встигло доїхати.

Останній рядок — найцінніший: видно і експоненційну затримку, і джитер
(294 і 364 мс замість рівних 220 і 440).

## Reflection (частина 3)

**Чому `Promise.all`, а не `await` у циклі?**
Бо послідовний варіант додає затримки одна до одної: 7 файлів × 120 мс = 840 мс
проти 257 мс паралельно. Заміряно, таблиця вище.

**Що робить `Promise.all` при помилці одного із запитів?**
Відхиляється одразу, але інші запити **не скасовує** — вони долітають
у порожнечу. Скасування — окрема робота для `AbortController`.

**Чому на 404 не можна повторювати?**
Бо результат не зміниться, а користувач чекатиме три спроби з backoff.
Повтор має сенс лише там, де причина тимчасова: 5xx, обрив, таймаут.

**Навіщо джитер у backoff?**
Щоб клієнти, які впали одночасно, не повторили запит теж одночасно
й не поклали сервер удруге.

**Чому `AudioContext` створюється на кліку, а не на завантаженні?**
Браузери блокують автовідтворення звуку: контекст, створений без жесту
користувача, лишається в стані `suspended`. «Join» — перший надійний жест.

**Як sim лишається незалежним від звуку?**
Він не імпортує `audio/` взагалі. Світ кидає події в `GameBus extends
EventTarget`, а підписується на них уже `audio.js`. Напрямок залежності
тільки один: від периферії до сима, ніколи навпаки.

**Чим `AbortSignal.timeout()` відрізняється від власного `setTimeout` + `abort()`?**
Нічим по суті, але він сам прибирає за собою таймер і дає `TimeoutError`
замість `AbortError` — тобто «сервер не відповів» відрізняється від
«користувач пішов» без жодного додаткового прапорця.
